# 이음 개발 및 배포 버전 관리

`main`은 Vercel 운영 배포용이며, 매일 작업 내용은 한국 시간 기준 `daily/YYYY-MM-DD` 브랜치에도 저장합니다. 같은 날 추가 수정은 해당 날짜 브랜치를 이어서 사용합니다. 저장소 이름과 배포 주소는 기존 것을 유지합니다.

## 변경 반영 순서

1. 원격 상태와 현재 수정 사항을 확인하고 날짜 브랜치를 생성하거나 이어서 사용합니다.
2. 기능을 구현하고 변경에 맞는 테스트, 타입 검사, 운영 빌드를 통과시킵니다.
3. 변경을 커밋하고 날짜 브랜치에 먼저 푸시합니다.
4. `origin/main`을 다시 확인합니다. 다른 변경이 있으면 병합하고 필요한 검증을 다시 실행합니다. 강제 푸시는 사용하지 않습니다.
5. 검증된 커밋을 `main`에 반영하고 `release/YYYY-MM-DD.N` 태그를 남깁니다. 같은 날 두 번째 배포는 `.2`입니다. 태그도 원격에 푸시합니다.
6. Vercel이 해당 커밋을 운영 주소에 배포했는지 확인합니다. 다음 작업은 날짜 브랜치에서 계속합니다.

날짜 브랜치는 하루의 작업 이력, 릴리스 태그는 실제 운영 버전을 찾는 기준입니다. 기존 태그를 이동하거나 덮어쓰지 않습니다. 과거 기능을 되돌릴 때는 당시 차이를 확인하고 되돌림 커밋을 만들어 새 릴리스로 배포합니다. DB의 개인 기록이나 게시된 공지는 코드 태그에 포함되지 않으므로 별도로 백업해야 합니다.

브랜치 Preview를 사용할 때는 운영 DB 대신 별도 테스트 DB를 설정합니다. 운영 계정 정보와 API 키는 코드·브랜치·태그·문서에 넣지 않습니다. 에이전트의 지속적인 작업 규칙은 루트 `AGENTS.md`에도 기록되어 있습니다.
